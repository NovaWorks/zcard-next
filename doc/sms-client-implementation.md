## 2026-10-01：独立接码渠道商品已实现

基于 `zcard-next/main` 的 v1.2.98（`6c895f8`）完成本地改造。每条供货端发布的渠道只采集一个 `product_kind=sms_channel` 商品，重复采集和同步更新原商品，不创建国家/平台明细商品或 SKU。沿用现有 ZCard 商品采集窗口设置零售加价；商品页面按需加载国家、平台及报价，会员余额购买后在同页查看号码、短信、取消、完成和零售价退款。已有明细商品流程继续兼容。

新接口均位于买家后端，成本、供货报价和凭据不返回买家：

| 入口 | 作用 |
|---|---|
| `GET /api/v1/storefront/products/{product_id}/sms/options` | 国家和平台选项 |
| `GET /api/v1/storefront/products/{product_id}/sms/offers` | 分页动态零售价 |
| `POST /api/v1/storefront/products/{product_id}/sms/quotes` | 冻结会员、商品、成本、零售价、版本和期限 |
| `GET /api/v1/storefront/products/{product_id}/sms/sessions` | 当前会员在该商品下的历史号码 |
| `POST /api/v1/storefront/orders` | 用 `sms_quote_id` 和原幂等键创建零售订单，金额由服务端读取报价 |

付款沿用余额支付接口；供货端购买使用 `sms_channel_purchase.v1` 和 `/api/supply/sms/channel-orders`，查单与动作沿用原协议。建单或付款响应丢失时确认同一零售订单，不生成第二笔采购。供货全额退款后按零售实付退款，成本和零售价分别记账。

新增 `sms_retail_quotes` 表与商品类型列；三种数据库迁移由 Atlas 生成，不复制私有迁移编号。新购默认开启，显式 `false` 仅暂停新购。

本轮验证通过：Go 全套、最后修改涉及模块与架构金额规则、签名 HTTP 契约、MySQL/PostgreSQL 并发建单/扣款/退款、前后台类型检查与生产构建、390px/1440px 浏览器响应丢失恢复和收码退款、fullstack 内嵌资源检查。Linux amd64/arm64 前后端合并二进制位于 `server/bin/`，指纹见同目录 `BUILD-INFO.json` 与 `SHA256SUMS`。未执行真实供应商付费取号，未推送或部署。下面保留的是原明细客户端的历史实施记录与真实供应商验收事项。

## 2026-10-01：独立渠道商品复查与修复

本轮按完整链路重新查阅采集、同步、商品可见性、报价/付款、后台任务和浏览器状态，并修复：

1. 渠道商品没有聚合库存，原定时采集/状态同步、仅库存补查、低库存巡检及详情库存刷新仍按普通商品调用，可能虚报库存失败、浪费上游请求并挤占普通商品巡检。现在跳过渠道聚合库存；普通库存自动上下架明确不适用，已有误开启的自动管理在观察时暂停，保留售卖状态。报价选项仍检查实际库存。
2. 未付款后过期的零售订单没有 SMS 任务，混入号码列表会使整页返回 404。号码列表排除这类订单，保留会员已付款会话。
3. 隐藏渠道商品允许会员购买，但详情接口原先仍返回不存在。现在主站会员可直接访问隐藏渠道商品，游客与其他 realm 仍不可见，响应禁止缓存；普通隐藏商品行为保持。
4. 取消/结束操作丢失响应时，上一笔操作的终态可能清掉本次浏览器操作标识。响应新增可选 `operation_request_id`，页面只使用同一请求的回执确认完成；未知响应保留原操作号，明确拒绝则解除待确认状态，review 显示待核对。
5. 首次空号码列表也设置 `Cache-Control: no-store, private`。账号切换或退出后，旧异步购买/余额结果不再写入新的页面状态。
6. 用户选择服务后再切换国家，平台重置与选项请求共用序号，可能丢掉新国家的列表。现在独立管理选项/报价请求和加载状态；已补测国家来回切换。专用页面移除重复面包屑与说明，缺货选项禁止选择，不限库存不显示负数数量。

新增回归覆盖各维护任务、35 个渠道不挤占普通商品低库存巡检、过期未付款订单与空历史缓存、隐藏商品身份边界、精确操作回执，以及桌面/手机国家切换和丢失取消响应时旧回执恢复。Go 全套、前端类型检查/构建、MySQL/PostgreSQL 零售接码与退款/巡检集成测试通过。浏览器验证使用隔离 API，无真实供应商付费取号。

最终 fullstack Linux amd64/arm64 二进制已重新构建，指纹以 `server/bin/BUILD-INFO.json`、`SHA256SUMS` 为准。源码尚未提交或推送，未部署生产。

## 功能范围

- 统一 ZCard HMAC 客户端，声明 `sms_activation.v1` / `sms_polling.v1`；每次真实 HTTP 发送重新签名。整数分、版本及 ID 避免浮点解码；不包含供应商品牌业务分支。
- 商品与订单项保存 `delivery_kind`、公开产品元数据、说明及固定采购意图。普通商品默认 `card`。接码不向本站下游供货接口开放。
- ZCard 导入按页加载，默认每页 50，支持高页码；每页独立快照。父分类优先创建，相同叶子名称不会跨父分类合并。页面搜索仅搜索当前页。目录变化可能移动页边界，不能把局部页当作全量缺失依据。
- 只允许 CNY、登录会员、余额支付、数量 1、单商品独立订单。禁用 SKU、购物车、优惠券、积分、营销折扣及返佣；拒绝有手续费的支付渠道。下单和付款前检查能力、账号身份、余额、实时库存及原价上限。
- 付款与 `sms_intents` 创建共用事务。持久保存原请求号、正文、摘要和供货账号身份；重启及未知响应后重放同一意图。创建请求不含 `callback_url`。
- 数据库 worker 每 5 秒调度，通常 8 秒后再次查询，按账号分组、最多 50 单。账号及订单项均有租约；有限重试、退避、Retry-After 和 CAS。单个坏订单导致批量失败时分拆定位，其他订单继续处理。
- `sms_operations` 保存取消/完成的固定操作号，独立跟踪 pending/succeeded/rejected。操作成功不等于资金已退。未知状态、版本矛盾、身份不符或重试耗尽进入人工核对。
- 号码、验证码、短信正文作为聚合快照加密保存；按 version/revision 防回退。有正文但无数字验证码也可交付，不从正文伪造验证码。接码内容不进入普通卡密交付通知。
- 仅完整拒绝回执，或核对过 CNY 供货扣款、全额退款和稳定参考号后，进入本地退款。通过订单原生 v0/v1 退款服务退零售剩余实付，任务参考号为 `sms_retail_refund:<order_item_id>`，与钱包及出箱事务一致。
- 订单详情内展示号码、独立复制、正文、租期和操作状态；正文按纯文本转义。可见页面约 4 秒读取本地 API，隐藏时降为 30 秒；关闭浏览器不停止后台任务。
- 后台“接码任务”显示任务状态、退款和诊断，恢复必须填原因并记录审计。恢复只重放原意图；完成任务不能重新采购。未完成任务阻止货源身份修改及连接删除。

## 开关和运维

接码新购默认启用，编译并正常启动即可使用，无需设置环境变量。仅显式设置 `ZCARD_SMS_SALES_ENABLED=false` 时暂停新购；暂停后已有订单继续收码、操作和退款。后台诊断页显示当前状态。

关闭新购后继续运行原服务及数据库 worker，已有订单仍需查单、追踪操作和退款。无需 Redis 或买家保持页面打开。连接停用也不会把历史意图改绑到另一个账号。

采购/查询故障退避后仍无法确认时，后台显示 `review`。管理员应核对原订单号、原供货账号及上游账务，再恢复原任务。不要手工修改请求正文、供货订单 ID、版本、退款金额或钱包流水。401/403、幂等冲突和不明结果都不能作为零售退款依据。

加密使用现有卡密加密服务，部署必须保留原有加密主密钥。历史号码和短信只能通过对应会员订单查询，买家接口返回 `Cache-Control: no-store, private`。

## 2026-09-30 第二轮复查

本轮重新检查 worker、操作状态、资金优先级和浏览器错误恢复。先用新增回归用例复现问题，再修复：

1. **账号故障放大请求**：批量查询遇到 429/401/403 或上下文取消时，不再二分重复请求；整批按原身份退避。缺少供货订单 ID 的异常行单独进入核对，不再中断其他正常行。
2. **过期 worker 回写操作**：操作失败分支原先没有完整租约栅栏，旧请求晚返回可能把新 worker 已确认的 `succeeded` 改成 `review`。现在成功、失败均在事务内校验租约 token 和有效期；采购回执保存也检查租约有效期。
3. **操作失败覆盖资金事实**：已确认供货退款的快照先进入零售退款阶段，不再被独立的取消/完成错误改回人工核对。买家页面也不会用过期操作警告覆盖已确认的退款进度。
4. **人工核对任务失去入口**：存在待核对操作时，即使会话已终结，也保留 `review` 阶段及后台恢复入口；不会被当作无未完操作而关闭任务。
5. **瞬时中断误判业务矛盾**：快照内容矛盾使用明确的核对错误类型；上下文取消、数据库瞬时失败和并发失败走有限退避，不会仅因服务重启/超时直接转人工。
6. **操作退避不增长**：健康快照不再导致连续操作失败计数永远停在 1；操作成功重置连续失败计数，正常 pending 响应不累计为失败。
7. **浏览器错误恢复**：明确 4xx 拒绝后释放未提交动作，允许根据新能力执行另一动作；保留错误提示。网络、408、429、5xx 等不明结果显示“重试确认”并使用原操作号。采用已有安全随机 ID 工具，兼容没有 `crypto.randomUUID()` 的 HTTP 环境。

新增测试覆盖限流只发送一次、旧 worker 不覆盖新结果、资金确认优先、终态操作可恢复、取消上下文后自动退避、连续操作失败计数增长、坏行隔离及买家退款展示。前台 fixture 增加 400 后切换动作、丢失响应后同号重试和禁用 randomUUID 的用例。

验证：后端全量 `go test ./...` 通过；最后追加的采购模块修正另跑完整采购模块通过；SMS 采购测试以 `-race -count=1` 通过。前台类型检查、生产构建、手机/桌面浏览器回归、fullstack manifest 检查及重建通过。没有修改数据库 schema 或退款金额计算，本轮未重跑 MySQL/PostgreSQL 集成线；上表该项仍是第一轮实测记录。
